# Render worker contract (M5)

The three.js render worker is the only armory portrait renderer. It claims portrait jobs from
the website's queue (`portraits.db`), renders them headless, and ingests the PNG. This file is the
contract between the website (`website/`) and the worker (`avatar/worker/`).

## Website side

- **Fingerprint v3** = first 16 hex of SHA-256 over
  `v3|r=<RENDERER_VERSION>|c=<catalog version>|p=front|<canonical recipe>`, where the canonical
  recipe is the recipe JSON (`lib/avatar-recipe.ts`) reduced to what changes pixels:
  `gender, skeleton{nif, scale, stance, idle}, parts{Folder: file}` for parts with `file` set and
  `exists` true (sorted by folder), `colors{hair, eyeRight, eyeLeft}`. `why` and `notes` are excluded.
  `RENDERER_VERSION` is a constant in `website/lib/portrait-renderer.ts` (start at `1`); bump it
  whenever the worker's output for the same recipe changes. Character name is **not** part of v3
  (same look → same PNG). The armory serves `portraits/{fingerprint}.png|.webp` only.
- **Enqueue**: on an armory miss, the job payload carries `{fingerprint, characterName, recipe,
  rendererVersion, preset: "front", width: 768, height: 925}`.
- **Availability**: armory misses enqueue only while a render worker on this `RENDERER_VERSION`
  has sent a heartbeat in the last 60 s; otherwise the page shows the placeholder.
- **Admin → Portraits** (`/admin/studio`): status (render worker online / offline, live armory
  stats), worker details, queue (enqueue one / bulk), clear one character. No token editing:
  `PORTRAIT_WORKER_TOKEN` comes from `deploy/.env` (generated by `install.sh`) and compose passes
  it to both the website and the `avatar-worker` service. A worker running elsewhere uses the
  same value copied from `.env`; `website/.env.local` sets it for local dev.

## HTTP (all with `X-Portrait-Worker-Token: <PORTRAIT_WORKER_TOKEN>`)

| Method | Path | Body | Response `data` |
| --- | --- | --- | --- |
| POST | `/api/portrait/worker/heartbeat` | `{workerId, kind: "three", rendererVersion, assetsVersion, chrome, busy}` | `{ok: true, rendererVersion, versionMismatch}` |
| POST | `/api/portrait/queue/claim` | `{kind: "three", rendererVersion?, workerId?}` | `{empty, job}`; `job` has `fingerprint`, `characterName`, `recipe`, `preset`, `width`, `height`, `rendererVersion`, `catalogVersion`. The worker's version comes from the body, else its last heartbeat, else the newest three heartbeat; unknown or different → `empty` with `versionMismatch`. A body without `kind: "three"` is a 400. Pending jobs of another `rendererVersion` (or legacy rows without a recipe) are failed, not claimed. |
| POST | `/api/portrait/queue/ingest` | multipart `fingerprint`, `file` (PNG) | as today |
| POST | `/api/portrait/queue/fail` | `{fingerprint, error}` | as today |

Responses use the site's usual `apiOk` / `apiFail` wrapper (`{success, message, data}`).
A worker whose `rendererVersion` differs from the website's must not claim (the website answers
claim with `empty: true` and a `versionMismatch` note).

## Worker

- Node service in `avatar/worker/`, reusing `avatar/viewer/buildScene.js` through the same
  headless page as `avatar/viewer/render.mjs` (one persistent browser + page, reused per job).
- Env: `PORTRAIT_QUEUE_URL`, `PORTRAIT_WORKER_TOKEN`, `AVATAR_ASSETS_DIR` (converted assets,
  default `avatar/build/assets`), `PORTRAIT_WORKER_ID`, `PORTRAIT_POLL_MS` (default 2000),
  `PORTRAIT_SSAA` (default 3), `CHROME`, `PLAYWRIGHT_CORE`, `THREE_DIR`.
- Loop: heartbeat every 15 s; claim; render recipe with `preset`, `width`, `height`, pose
  `stance`, glow off; ingest; on error call fail with the message. One job at a time.
- Golden test: `avatar/worker/golden.mjs` renders fixed recipes and compares SHA-256 with
  `avatar/worker/golden.json` (hashes only — no images committed, since they are derived from game
  assets). Hashes are per Chrome build; the file records the build they were made with.
